# FITBEST 统一智能训练平台 · 系统设计方案

> 版本：v2.0（2026-11-16）
> 变更记录：
> - v2.0：**后端技术架构由 NestJS（Node.js）变更为 Java（Spring Boot）**；原 fit-best-api 及 7 个独立部署站点（/hyrox/、/btwe/、/fitbestwebsite/、/console/ 等）**合并为统一服务、统一后端**，静态站全部接入统一服务托管
> - v1.0：基于现状代码库的初始设计（NestJS + 分散部署）

---

## 1. 项目概述

### 1.1 产品定位

FITBEST 是一套**连接智能健身器械的训练平台**，面向健身房 / 训练中心场景：

- **C 端**：用户通过手机 / 平板蓝牙连接器械，完成单机训练、力量训练、赛事训练（HYROX / BTWE），查看统计并分享
- **B 端**：门店与组织管理器械、用户、训练数据与赛事运营

### 1.2 v2.0 架构目标

| # | 目标 | 说明 |
|---|---|---|
| 1 | **统一服务** | 一个 Spring Boot 单体应用（fitbest-server）承接全部流量：REST API + 分享页 + 全部前端静态站 |
| 2 | **统一后端（Java）** | 原 NestJS 后端按**API 契约 100% 兼容**原则重写为 Java，已对接的前端（hyrox / btwe / admin）零改动 |
| 3 | **统一部署** | 单 docker compose 栈（server + postgres + redis），一个域名一套路径，消除 8 个子项目分散部署的现状 |
| 4 | **统一数据** | 数据库 Schema 保持不变（22 张表），Java 侧以 Flyway 基线接管，业务数据无缝延续 |

### 1.3 用户角色

| 角色 | 说明 | 入口 |
|---|---|---|
| 游客 | 免登录体验，本地数据 | /fitbest/ |
| 注册用户 | 短信 / 邮箱 / 微信 / 密码登录 | /fitbest/、/hyrox/、/btwe/ |
| 管理员 | super / org_admin / gym_admin / ops / viewer | /fit-best/ |

### 1.4 产品矩阵（目标形态）

| 站点 | 路径 | 形态 | 现状 |
|---|---|---|---|
| fitbest（主训练 App） | `/fitbest/` | 手机 PWA + Android/iOS 原生 | UI 完成，API 待接入 |
| fitbest HD | `/fitbest-hd/` | 平板横屏版 | 同上 |
| hyrox-trainer | `/hyrox/` | PWA | 已接 API（契约不变则零改动） |
| btwe-trainer | `/btwe/` | PWA | 已接 API（契约不变则零改动） |
| fit-best-admin | `/fit-best/` | Web 管理后台 | 已接 API（契约不变则零改动） |
| 官网 | `/fitbestwebsite/` | 静态页 | 接入统一服务 |
| 仪表模拟器 | `/console/` | 静态页 | 接入统一服务 |
| 统一后端 | `/api/v1/*`、`/s/*` | Spring Boot | 由 NestJS 重写 |

### 2.2 模块合并映射

原 8 个子项目收敛为「**1 个统一服务 + N 个前端构建源**」：

| 原工程 | 去向 |
|---|---|
| fit-best-api（NestJS） | 重写为 `fitbest-server`（Java），完成后归档下线 |
| fit-best-trainer | 保留为前端工程，构建产物 → server 静态目录 `fitbest/`、`fitbest-hd/` |
| hyrox-trainer / btwe-trainer | 保留为前端工程，产物 → `hyrox/`、`btwe/` |
| fit-best-admin | 保留为前端工程，产物 → `fit-best/` |
| fitbest-website / rowing-console-simulator | 产物 → `fitbestwebsite/`、`console/` |
| rowing-console-mockup | 内部原型，不接入 |

**目标工程结构：**

```
fitbest/
├── fitbest-server/          # 统一后端（Spring Boot，本次新建）
├── fit-best-trainer/        # 前端：主 App（保留）
├── hyrox-trainer/           # 前端：HYROX（保留）
├── btwe-trainer/            # 前端：BTWE（保留）
├── fit-best-admin/          # 前端：管理后台（保留）
├── fitbest-website/         # 前端：官网（保留）
├── rowing-console-simulator/# 前端：仪表模拟器（保留）
└── docs/                    # 设计文档
```

### 2.3 统一路由总表（fitbest-server 承接全部）

| 路径 | 类型 | 处理 |
|---|---|---|
| `/api/v1/**` | REST | 各业务 Controller |
| `/s/{code}` | SSR | 分享落地页（含 OG meta） |
| `/fitbest/**`、`/fitbest-hd/**` | 静态 SPA | trainer 手机版 / HD 版，fallback 各自 index.html |
| `/fit-best/**` | 静态 SPA | admin（注意与 API 前缀区分：API 为 `/fit-best/api/v1`，**由 Nginx rewrite 去掉 `/fit-best` 前缀后转发**，保持已上线前端零改动） |
| `/hyrox/**`、`/btwe/**` | 静态 SPA | 赛事端 |
| `/fitbestwebsite/**`、`/console/**` | 静态 | 官网 / 模拟器 |
| `/actuator/health` | 运维 | 健康检查（仅内网） |

> 兼容性关键点：hyrox / btwe / admin 前端写死请求 `/fit-best/api/v1`（相对路径）。统一服务对外仍暴露 `/fit-best/api/v1`（Nginx 或 server 端 rewrite → `/api/v1`），**已接好的三个前端完全不动**。

### 2.4 部署拓扑

```
服务器（阿里云 ECS · demo.thinkfit.cn）
└── docker compose（fitbest 栈）
    ├── nginx        （已有容器，配置精简为：TLS + 反代 8080 + 静态缓存头）
    ├── fitbest-server  （Spring Boot，仅绑内网，暴露 8080）
    ├── postgres:16-alpine（卷持久化，不暴露端口）
    └── redis:7-alpine   （AOF，不暴露端口）
```

- 原 `pcba-net` 上不再需要 `fitbest-api` 别名，统一栈独立组网（`fitbest-net`）
- Nginx 从「7 个 location 分散静态 + 反代」简化为「1 个反代 + 缓存策略」

### 3.3 B 端管理后台（/fit-best/）

### 3.4 API 契约要点（Java 重写的验收基准）

| 约定 | 内容 |
|---|---|
| 路径前缀 | `/api/v1/*`（对外网关别名 `/fit-best/api/v1`） |
| 成功响应 | 直接返回业务数据（无 envelope） |
| 失败响应 | HTTP 4xx/5xx + `{ code: number, message: string }` |

## 4. Java 后端详细设计

### 4.1 技术架构分层

```
Controller（REST + Bean Validation）
    ↓
Service（业务逻辑 · 事务边界）
    ↓
Repository（Spring Data JPA）
    ↓
PostgreSQL / Redis

横切：Security 过滤器链 · AOP 审计 · 全局异常处理 · 配置中心（application.yml + env）
```

- **模块化单体（Modular Monolith）**：按业务域分包，包间只通过 Service 接口调用，禁止跨包访问 Repository —— 保留未来拆分能力，当前不引入微服务复杂度
- **虚拟线程**：`spring.threads.virtual.enabled=true`（Java 21），I/O 密集（DB / Redis / 外部 HTTP）场景高并发低开销

### 4.2 包结构（fitbest-server）

```
com.ifitbest.server
├── common/                  # 横切
│   ├── error/               # BizException + 全局异常处理（保持 {code,message} 契约）
│   ├── security/            # 双过滤器链、JWT 编解码、CurrentUser 注解
│   ├── audit/               # AOP 审计（管理端写操作 → audit_logs）
│   ├── web/                 # 静态资源托管配置、SPA fallback、日志 MDC
│   └── util/                # QR HMAC、时间、分页
├── module/
│   ├── auth/                # 认证：验证码(Redis)、登录注册、refresh 轮换、注销
│   ├── user/                # 资料、身份绑定、目标、注销（软删除）
│   ├── session/             # 器械训练会话 + 周统计（幂等键）
│   ├── record/              # 赛事训练记录（clientKey 去重）
│   ├── device/              # 设备登记 + 会话同步（clientSessionId 幂等 + segments）
│   ├── machine/             # 器械、型号、标签、扫码解析
│   ├── event/               # 赛事外链 + 报名
│   ├── coach/               # AI 教练（LLM 客户端 + 规则降级 + 计划引擎）
│   ├── share/               # 分享短链 + SSR 页面 + OG
│   ├── notification/        # 站内通知
│   └── admin/               # 管理端聚合查询 + 主数据维护 + 数据域隔离
└── infra/
    ├── persistence/         # JPA 实体（19 张表）、Flyway
    ├── redis/               # 验证码 / 冷却 / 日限组件
    └── integration/         # 阿里云 SMS/DM、微信(WxJava)、LLM(WebClient)
```

### 4.3 认证与安全设计

**Spring Security 三条过滤器链：**

| 链 | 匹配 | 机制 |
|---|---|---|
| 管理链 | `/api/v1/admin/**` | JWT_ADMIN_SECRET 签发的 token + AdminRole 权限 + 审计 AOP |
| 用户链 | `/api/v1/**`（除公开端点） | JWT_ACCESS（15m）；refresh（30d）哈希存 `user_sessions`，支持撤销 / 轮换 / 注销 |
| 公开链 | `/s/**`、静态站、`/api/v1/auth/*`、`/api/v1/events`、`/api/v1/machines`、`/actuator/*` | 放行（events 可选鉴权） |

**JWT 实现**：jjwt（HS256，双密钥隔离用户 / 管理端），与原 NestJS jsonwebtoken 输出兼容（前端不感知差异）。

**验证码（Redis）**：TTL 300s、发送冷却 60s、日限 10 条 —— 键设计与原实现一致（`code:{scene}:{target}`、`cooldown:{target}`、`daily:{target}:{date}`），**迁移期间两套后端可共存校验**。

### 4.4 关键机制实现映射（NestJS → Java）

| 机制 | NestJS 现实现 | Java 目标实现 |
|---|---|---|
| 入参校验 | zod schema + ZodPipe | Bean Validation 注解 + `@Valid`；跨字段规则（如"手机/邮箱需且仅需一个"）在 Service 层校验 |
| 统一异常 | HttpExceptionFilter | `@RestControllerAdvice`，错误结构 `{code, message}` 不变 |
| 幂等 | 唯一约束 + upsert | JPA + 原生 SQL `INSERT ... ON CONFLICT DO NOTHING/UPDATE`（PG 特性），保留唯一约束兜底 |
| 管理端审计 | audit.interceptor | `@Audit` 注解 + AOP 环切，写 audit_logs |
| 多租户过滤 | tenant.ts（角色 → 数据域） | `AdminScope` 上下文对象 + Repository 层 Specification 拼接 |
| 定时/后台 | 进程内 | `@Scheduled`（如分享过期清理、通知聚合） |
| 配置 | config.ts + dotenv | `application.yml` + 环境变量覆盖（12-factor） |

### 4.5 外部集成

| 服务 | Java 方案 |
|---|---|
| 阿里云短信 / 邮件 | 阿里云官方 SDK（dysmsapi / dm），统一 `MessageGateway` 接口 + message_logs 落库 |
| 微信开放平台 | WxJava（weixin-java-open / mp），app / web 双客户端 |
| LLM（AI 教练） | Spring `WebClient`，OpenAI 兼容 `/chat/completions`；20s 超时 + 熔断降级到内置规则引擎（无 key 场景与现行为一致） |

### 4.6 API 文档与测试

- **SpringDoc OpenAPI 3**：`/v3/api-docs` + Swagger UI（仅开发环境开启），以契约文档辅助前后端对齐
- **测试**：JUnit 5 + Testcontainers（PG / Redis 真实容器）+ MockMvc；**每个迁移模块编写契约回归测试**（对照 NestJS 响应快照）

## 5. 静态站统一接入设计

### 5.1 资源目录规划

静态资源**外置目录**（前端发版不动 jar）：

```
服务器 /opt/fitbest/web/
├── fitbest/          # trainer 手机版（vite build）
├── fitbest-hd/       # trainer HD 版（build:hd）
├── fit-best/         # admin
├── hyrox/            # hyrox-trainer
├── btwe/             # btwe-trainer
├── fitbestwebsite/   # 官网
└── console/          # 仪表模拟器
```

Spring `WebMvcConfigurer.addResourceHandlers` 将 7 个路径映射到上述目录；volume 挂载进容器。

### 5.2 SPA fallback 与缓存策略

| 站点 | fallback | 缓存 |
|---|---|---|
| 5 个 SPA（fitbest / hd / admin / hyrox / btwe） | 未命中资源 → 各自 `index.html`（`/fitbest/` 前缀隔离，互不串扰） | `index.html` → `no-cache`；带 hash 的 js/css/图片 → `max-age=31536000, immutable` |
| 官网 / 模拟器 | 无需 | `max-age=7d` |

- PWA Service Worker 更新依赖 index.html no-cache 策略，保持 `vite-plugin-pwa` autoUpdate 行为不变
- trainer 原生包不受影响（资源离线打包）

### 5.3 前端发布流程（统一）

全量发布从项目根目录执行。先根据 `fitbest-server/.env.example` 准备 `fitbest-server/.env`。

```sh
docker compose -f fitbest-server/docker-compose.yml -f fitbest-server/docker-compose.release.yml up -d --build
```

- Compose 按锁文件构建前端，并将七个站点和两个赛事 HD 子站一次发布到同一个只读挂载。发布镜像中的网页使用同源 `/api/v1`。
- 已安装前端依赖时，也可用 Node 24 执行 `node fitbest-server/deploy/build-web.mjs <空目录>` 构建同一套产物。
- 使用原有宿主机静态站目录时，单独使用基础 Compose 文件，并配置 `FITBEST_WEB_DIR`。

### 5.4 GitHub Actions 发布

提交到 `main` 或向它发起 PR 时，GitHub Actions 构建 Web 产物，并运行前端测试、Java 测试以及 PostgreSQL/Redis 集成测试。推送到 `main` 或推送 `vX.Y.Z` 标签时，测试通过后构建并启动 Compose 栈做冒烟检查，然后将 `fitbest-server` 和 `fitbest-web` 镜像发布到 GHCR。主分支构建使用 `sha-<完整提交 SHA>`，版本构建使用 Git 标签。

在部署机上，保留原有 Compose 项目名及 `fitbest-server/.env`。使用相同的镜像标签拉取并部署这两个镜像。若镜像包需要授权，先通过有包读取权限的账号使用 `docker login ghcr.io` 登录。

```sh
cd fitbest-server
export FITBEST_RELEASE_TAG=v0.1.0  # 改为已发布的标签
export COMPOSE_FILE=docker-compose.yml:docker-compose.release.yml:docker-compose.registry.yml
docker compose pull
docker compose up --no-build --wait
```

## 6. 数据库设计

V1–V5 延续原 Prisma 数据库结构，后续版本由 Flyway 迁移。

### 6.1 ORM 接管策略（已实施）

- 原 Prisma 的 5 个 migration **原样接管**为 Flyway `V1__init.sql` ~ `V5__device_sessions.sql`（SQL 与线上最终态完全一致）
- `baseline-on-migrate + baseline-version=5`：空库从 V1 执行。旧库接管前检查 V5 所需的表、列、约束及可用的 Prisma 迁移历史，检查通过后从 V6 继续。
- 之后一切变更走 Flyway（从 `V6__` 起），禁止手改线上库
- JPA 实体按域分包（`infra.persistence.session` 等），JSON 字段（specs / metrics / moduleTimes / runSplits / weeklyPayload）映射为 `@JdbcTypeCode(SqlTypes.JSON)` + String/JsonNode

### 6.2 保留的关键设计（实现于 Java 侧）

| 要点 | 说明 |
|---|---|
| 幂等三件套 | `sessions.idempotency_key` 唯一；`training_records(userId, app, clientKey)` 唯一；`device_sessions(userId, clientSessionId)` 唯一 |
| 软删除 | users.deletedAt；强依赖数据（身份/会话）级联删除 |
| 复合索引 | sessions 三组 `(xxx, startedAt desc)` 直接支撑高频查询 |
| Decimal 精度 | 身高体重 / 速度，禁浮点 |
| UUID 主键 | 全库 `@db.Uuid`，JPA 用 `UUID` 类型 + 应用侧生成 |

### 7.4 选型评审结论

- **为什么 Spring Boot 单体而非微服务**：当前规模（12 业务域 / 40+ 端点 / 单服务器）下，微服务只会增加运维成本；模块化单体 + 包边界约束已满足"统一服务"目标与演进空间
- **为什么 JPA 而非 MyBatis-Plus**：本项目以标准 CRUD + 少量聚合查询为主，JPA 实体即文档、与 Flyway 配合好；管理端复杂查询用 Specification / 原生 SQL 补充
- **为什么保留 PostgreSQL schema**：迁移只换应用层，数据层零风险，且已上线前端（hyrox / btwe / admin）依赖的数据语义不变
- **风险最低路径**：API 契约 100% 兼容 + 数据库不动 → 前端与存量数据双零改动

## 8. 实施计划与迁移策略

### 8.1 三阶段推进

```
阶段一：统一服务骨架 + 静态站收敛（不动后端逻辑）
  ① fitbest-server 骨架（Spring Boot + Security + 异常契约 + Flyway 基线）
  ② 静态资源托管 + SPA fallback + 缓存策略（§5）
  ③ 7 个站点产物迁入 /opt/fitbest/web/，Nginx 切换为统一反代
  ④ 验收：全部站点在统一服务下可访问（此阶段 API 仍由 NestJS 承接，
     Nginx 将 /fit-best/api 与 /s 临时反代到旧 fitbest-api）

阶段二：API 模块逐个迁移（新旧并行，灰度切换）
  迁移顺序（依赖排序）：
  ⑤ auth + users（认证是全链路地基）
  ⑥ machines / scan（器械 + 扫码）
  ⑦ sessions / stats → records → devices（训练数据链）
  ⑧ events / notifications / share（含 /s SSR）
  ⑨ coach（LLM + 降级）
  ⑩ admin（聚合查询 + 审计，最后迁移）
  每模块：Java 实现 + 契约回归测试（对照 NestJS 响应）→ Nginx 按
  location 前缀灰度切流 → 观察无 diff 后下一模块

阶段三：切换与收尾
  ⑪ 全量流量切 fitbest-server；NestJS 容器停机归档
  ⑫ fit-best-trainer 接入真实 API（可与阶段二并行）
  ⑬ 安全收尾：CORS 白名单、密钥轮换、超管改密、备份策略
  ⑭ 原生 App 打包（Android bundle / iOS）
```

### 8.2 灰度与回滚

- Nginx location 级切换：`/fit-best/api/v1/auth/*` 指向 Java、其余仍指 NestJS，出问题 30 秒内改回
- 两套后端共用同一 PG / Redis（验证码键结构一致），用户会话（JWT + user_sessions 表）天然互通，**切换对在线用户无感**
- 数据库始终只有一份，无数据迁移风险

### 8.3 工作量评估（粗粒度）

| 模块 | 说明 |
|---|---|
| 骨架 + 静态接入 | 框架搭设、安全链、异常契约、资源映射 |
| auth / users | 验证码 Redis、四种登录、refresh 轮换、身份绑定 |
| 训练数据三模块 | sessions（幂等）/ records / device-sync（segments 批量） |
| machines / events / share | 含 QR HMAC、/s SSR |
| coach | LLM WebClient + 规则降级 + 计划引擎 |
| admin | 10+ 聚合端点、租户过滤、审计 AOP |
| 契约回归测试 | 全端点快照对照 |

## 9. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 契约不完全兼容导致已上线前端异常 | 高 | 契约回归测试（响应快照对照）+ location 级灰度 + 30s 回滚 |
| 重写工作量超预期 | 中 | 模块依赖排序、并行推进 trainer 接 API；阶段一先完成静态统一（独立价值） |
| 微信 / 阿里云 SDK 行为差异 | 中 | 集成测试 + message_logs 全量落库比对 |
| 双后端并行期数据一致性 | 低 | 共库共 Redis、幂等键一致；并行期不做 schema 变更 |
| 静态资源路径冲突（/fit-best 下 admin 与 API 前缀） | 低 | Nginx 精确 location 优先级：`^~ /fit-best/api/` 先于 `/fit-best/` |
| JPA JSON 字段 / Decimal 映射细节 | 低 | Testcontainers 实库测试覆盖 |
